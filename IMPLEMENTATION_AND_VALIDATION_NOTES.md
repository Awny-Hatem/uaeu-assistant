# Chatbot repair implementation and validation notes

This document tracks execution of `CHATBOT_REVIEW_AND_FIX_PLAN.md`. The audit remains a historical record of the pre-repair findings. The final round-ten review passed prototype/team-testing acceptance: 95 verified substantive answers, two appropriate clarifications, three safe limitations and zero defects in the 100-question sample. A passing mock test is not treated as verified answer quality. Git publication and public deployment identity are separately verified release steps, not implied by local acceptance.

## Validation design

- Freeze 100 independently authored questions before examining repaired answers.
- Cover academic courses, programs, admissions, registration, deadlines, documents, fees, financial support, housing, transport, IT, library, health, wellbeing, accessibility, careers, student life, privacy, safety, Arabic and context switching.
- Execute topic groups in a seeded random order while retaining chronological order inside conversations. This is topic-stratified coverage, not a statistical sample of every possible question.
- Preserve the actual question, full preceding request context, answer, citations, route/provider, latency, status and timestamps. Never rewrite the actual response to make it appear correct.
- Separate verified substantive answers, necessary clarification, safe information gaps, defects and unreviewed outputs. Do not count a missing answer as full coverage merely because it avoids hallucination.
- Keep the baseline and every later run. A regression fix can be retested, but the original failure remains in the evidence.

## Problems and decisions identified during implementation

1. The old deployment routed 72 of the independent 100 turns to escalation, 20 to generated retrieval, seven to FAQ and one to a guide. These are route counts, not correctness scores.
2. Current housing information differs from the older handbook. The current graduate student account page says graduate housing is not provided. An older postgraduate fee must not be presented as a current offer merely to satisfy a legacy test.
3. Course catalogs and cohort study plans can differ, particularly lab/co-requisite arrangements. Keep version and cohort scope and do not silently combine conflicting rules.
4. Library opening hours, reference-staff availability, and branch/season scope must stay distinct. Published facts should be supplied directly rather than replaced by a website-only response.
5. The prototype does not have verified institutional identity, a durable managed multi-instance account store, shared daily quotas or shared rate limits. These are production prerequisites, not defects that can be honestly closed by a local-only patch. No external service is provisioned without an agreed deployment design.
6. Self-declared university email addresses do not establish identity or justify a higher trusted allowance. Local account labels and tests must reflect this.
7. The Word authoring/rendering runtime is unavailable in this Windows workspace. The shareable deliverables are self-contained printable HTML and Markdown, backed by machine-readable JSON. No unrendered Word document is represented as visually verified.
8. Browser fault tests exposed a quota double increment caused by writing storage inside a React state updater. The write now occurs once in the response event handler, with a browser regression crossing UAE midnight under development StrictMode.
9. The 72-byte bcrypt boundary is now enforced on login and signup. A legacy prototype account created with a password longer than 72 UTF-8 bytes needs a verified recovery/recreation process; accepting that password would preserve the old suffix-collision behavior. No existing account records were deleted. Password reset and institutional SSO require a separate identity/recovery design.

## Release gate

Do not claim every possible question is verified. Release evidence must identify the exact tested build/content, real-provider question results, unresolved information needs, and browser/security test results. If material answer defects remain, do not use the earlier conditional permission to push to main as a reason to publish a failed build.
